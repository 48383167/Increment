# 全局异常处理机制 (Global Exception Handler)

**版本**: 2026-04-27
**所属模块**: `lin-core`

## 1. 为什么需要全局异常处理？

在没有全局异常处理的项目中，开发者常常面临以下困境：
- **满篇 try-catch**：为了防止异常导致系统崩溃，每个接口都写满了冗长的 `try-catch` 代码块，业务逻辑被掩盖。
- **报错裸奔**：如果漏掉了 `try-catch`，Java 原生的错误堆栈（甚至包含 SQL 异常）会直接暴露给前端用户，导致用户体验极差，且存在严重的安全风险。
- **状态不一致**：发生异常时，前端可能收到的是 Tomcat 原生的 500 HTML 错误页，无法按照预定的 JSON 格式去解析错误。

## 2. 结构构造

我们在当前包下构建了异常接管体系，主要由两部分组成：

### 2.1 自定义业务异常 (`BusinessException.java`)
继承自 `RuntimeException`。它的目的是打破业务执行流。只要遇到不符合业务规则的情况（如“库存不足”、“无权操作”），直接 `throw new BusinessException("提示语")`，剩下的交给框架处理。

### 2.2 全局异常处理器 (`GlobalExceptionHandler.java`)
核心利用 Spring 的 `@RestControllerAdvice` 和 `@ExceptionHandler` 切面机制拦截所有脱离 Controller 的异常。

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    // 1. 拦截主动抛出的业务异常，提取提示信息，返回业务状态码
    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusinessException(BusinessException e) { ... }

    // 2. 拦截未知系统异常，统一兜底返回 "系统异常"，避免暴露堆栈
    @ExceptionHandler(Exception.class)
    public Result<Void> handleException(Exception e) { ... }
}
```

## 3. 作用与优势

- **业务代码极致纯粹**：Service 层可以直接抛出 `BusinessException` 来中断执行，再也不需要层层传递 boolean 或错误码。
- **兜底保护**：无论系统发生何种空指针、数据库宕机还是算术异常，都会被 `handleException` 捕获并包装成统一的 `Result` 返回给前端，系统永远不会向用户抛出白板报错页。
- **方便排查**：在 Handler 中统一集成了 SLF4J 的 `log.error` 和 `log.warn`。错误日志集中输出，方便后续对接 ELK 等日志监控系统。
