# 统一返回结构设计 (Result)

**版本**: 2026-04-27
**所属模块**: `lin-common`

## 1. 为什么需要统一返回结构？

在企业级项目开发中，前端与后端的交互需要一个标准的契约。如果不对 Controller 的返回值进行约束，会导致以下问题：
- **格式混乱**：有的接口返回纯文本，有的返回 JSON，有的返回布尔值。
- **状态不透明**：当请求出错时，前端无法通过固定的字段判断是业务错误、权限错误还是系统崩溃。
- **解析痛苦**：前端不得不为每个接口编写单独的解析逻辑，极大地增加了前后端联调的成本。

## 2. 结构构造

我们在当前包下设计了全局唯一的响应封装类 `Result<T>`。其核心结构由三个字段组成：

```java
public class Result<T> implements Serializable {
    // 状态码：区分请求结果的大类状态（如 200 成功，400 参数错，500 系统错，600 业务错）
    private Integer code;
    
    // 提示信息：直接面向前端的文本提示，前端可直接将其用于弹窗提示（如 "用户名或密码错误"）
    private String msg;
    
    // 实际数据：使用泛型 T 保证类型安全与扩展性。可以是对象、集合或 null
    private T data;
}
```

配套使用枚举 `ResultCode` 来统一定义所有的核心状态码，避免在代码中到处写死魔法数字。

## 3. 作用与优势

- **统一契约**：所有接口格式保持绝对一致，前端只需要写一次全局拦截器，就能解析所有接口的状态。
- **化繁为简**：提供了一系列静态工厂方法（如 `Result.success(data)` 和 `Result.error(msg)`），使后端组装数据的代码极其简洁。
- **可扩展性**：支持泛型，可以无缝包装任何 DTO/VO 数据。对于无返回数据的操作类接口，支持使用泛型 `Result<Void>` 并通过 `Result.success()` 快速返回。

## 4. 使用规范

- **强制要求**：所有的 Controller 接口方法，其返回值必须且只能是 `Result<T>`。
- **禁止行为**：禁止在 Service、Manager 或 DAO 层返回 `Result` 对象。`Result` 仅作为 Web 层的对外输出。
