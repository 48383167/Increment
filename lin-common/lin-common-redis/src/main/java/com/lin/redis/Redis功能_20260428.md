# Redis 模块 (lin-common-redis)

**版本**: 2026-04-28
**所属模块**: `lin-common-redis`

## 1. 为什么需要 Redis 模块？

在 Spring Boot 项目中直接使用 `redisson-spring-boot-starter` 会面临以下问题：
- **序列化不统一**：默认使用 Redisson 自带的编解码器，与项目 Jackson 配置不一致，导致日期格式、大数字处理等行为不一致。
- **Key 管理混乱**：多个模块各自维护 Redis Key，容易出现 Key 冲突或难以追踪的问题。
- **配置分散**：Redisson 的连接池、线程等参数分散在 `application.yml` 各处，缺少统一管理。
- **工具缺失**：没有封装的 `RedisUtils`，每次操作都要手动获取 `RedissonClient`。

本模块在 Redisson 之上做了一层封装，统一序列化、Key 前缀、配置管理，并提供了开箱即用的 `RedisUtils` 和跨模块 Key 冲突自动检测能力。

## 2. 结构构造

### 2.1 自动配置 (`RedisConfig.java`)

通过 `@AutoConfiguration` 自动激活。核心行为：

- **统一序列化**：使用 `CompositeCodec`（StringCodec 处理 Key + TypedJsonJacksonCodec 处理 Value），确保存入 Redis 的数据与项目 Jackson 配置一致（日期 `yyyy-MM-dd HH:mm:ss`、大数字转字符串等）。
- **全局 Key 前缀**：通过 `KeyPrefixHandler` 实现 `NameMapper`，所有 Key 自动加上 `redisson.key-prefix` 前缀。例如 `key-prefix: lin` 时，`myKey` 实际存储为 `lin:myKey`。
- **线程池调优**：支持配置 Redisson 工作线程数和 Netty 线程数。
- **连接池管理**：单节点和集群两种模式，可分别配置超时时间、连接池大小、最小空闲连接数等。
- **Lua 脚本缓存**：开启 `useScriptCache`，减少网络传输。

### 2.2 配置属性 (`RedissonProperties.java`)

`@ConfigurationProperties(prefix = "redisson")` 绑定：

| 配置项 | 类型 | 说明 |
|--------|------|------|
| `key-prefix` | String | Redis Key 全局前缀 |
| `threads` | Integer | Redisson 工作线程数 |
| `netty-threads` | Integer | Netty 线程数 |
| `single-server-config` | 内嵌对象 | 单节点连接池参数 |
| `cluster-servers-config` | 内嵌对象 | 集群连接池参数 |

### 2.3 Key 前缀处理器 (`KeyPrefixHandler.java`)

实现 Redisson 的 `NameMapper` 接口：
- `map(name)` → 写入 Redis 前自动加前缀
- `unmap(name)` → 读取 Redis 后自动去前缀

### 2.4 Redis 工具类 (`RedisUtils.java`)

静态工具类，封装常用操作：

| 分类 | 方法 |
|------|------|
| **通用** | `setCacheObject`, `getCacheObject`, `deleteObject`, `isExistsObject`, `expire`, `getTimeToLive` |
| **扫描** | `keys` (按 pattern 扫描), `deleteKeys` (按 pattern 批量删除) |
| **List** | `setCacheList`, `getCacheList`, `addCacheList` |
| **Set** | `setCacheSet`, `getCacheSet`, `addCacheSet` |
| **Map** | `setCacheMap`, `getCacheMap`, `setCacheMapValue`, `getCacheMapValue`, `delCacheMapValue` |
| **原子** | `setAtomicValue`, `getAtomicValue`, `incrAtomicValue`, `decrAtomicValue` |
| **限流** | `rateLimiter(key, rateType, count, time, timeout)`, `getClientId()` |

> 限流方法供 `lin-common-ratelimiter` 模块调用，实现分布式限流。

### 2.5 客户端注入器 (`RedisClientInitializer.java`)

启动时自动将 Spring 容器中的 `RedissonClient` 注入到 `RedisUtils` 静态字段中。仅当容器中存在 `RedissonClient` Bean 时才激活。

### 2.6 Redis Key 前缀冲突检测器 (`RedisKeyConflictChecker.java`)

启动时自动收集所有实现了 `RedisKeyPrefixProvider` 的 Bean，逐一比对前缀，发现重复时输出 ERROR 日志告警。详见第 5 节。

## 3. 依赖项 (Dependencies)

## 4. 配置示例

### 4.1 单节点模式（默认）

```yaml
spring:
  data:
    redis:
      host: localhost
      port: 6379
      password: 123456
      database: 0
      timeout: 10s

redisson:
  key-prefix: lin
  threads: 16
  netty-threads: 16
  single-server-config:
    client-name: ${spring.application.name}
    connection-minimum-idle-size: 8
    connection-pool-size: 32
    idle-connection-timeout: 10000
    timeout: 3000
    subscription-connection-pool-size: 50
```

### 4.2 集群模式

```yaml
spring:
  data:
    redis:
      cluster:
        nodes:
          - 192.168.1.1:6379
          - 192.168.1.2:6379
          - 192.168.1.3:6379
      password: 123456

redisson:
  key-prefix: lin
  cluster-servers-config:
    master-connection-pool-size: 32
    slave-connection-pool-size: 32
    master-connection-minimum-idle-size: 8
    slave-connection-minimum-idle-size: 8
```

## 5. 跨模块 Redis Key 管理设计

### 5.1 设计动机

多模块项目中，每个模块都可能往 Redis 写数据——限流模块写限流计数、缓存模块写业务缓存、消息模块写队列。如果各模块在代码里散落硬编码的 Key 字符串，会出现三个问题：

1. **Key 难以追踪**：排查问题时不知道 `"rate_limit:/api/user:123"` 是哪个模块写的。
2. **前缀冲突风险**：两个模块不约而同用了 `"cache:"` 前缀，互相覆盖数据。
3. **重构困难**：改一个前缀要全局搜索字符串，容易遗漏。

### 5.2 方案：接口 + Spring 自动收集 + 启动校验

关键设计约束——**各个模块不能因为 Key 管理而增加对 Redis 模块的强依赖**。因此接口定义在 `lin-common-core` 中（零 Redis 依赖）：

```java
// lin-common-core — 纯接口，无任何 Redis 相关 import
@FunctionalInterface
public interface RedisKeyPrefixProvider {
    String getPrefix();  // 返回该模块在 Redis 中的命名空间
}
```

各模块创建自己的 Key 管理类，实现该接口并注册为 Spring Bean：

```java
// lin-common-ratelimiter — 限流模块
@Component
public class RateLimiterRedisKeys implements RedisKeyPrefixProvider {
    public static final String PREFIX = "rate_limit";     // 模块前缀
    public static final String KEY_PREFIX = PREFIX + ":"; // 供代码拼接用

    @Override
    public String getPrefix() { return PREFIX; }
}
```

```java
// lin-common-redis — Redis 模块自身
@Component
public class RedisKeys implements RedisKeyPrefixProvider {
    public static final String PREFIX = "cache";
    // 工具方法示例
    public static String cacheKey(String name) {
        return PREFIX + ":object:" + name;
    }

    @Override
    public String getPrefix() { return PREFIX; }
}
```

### 5.3 冲突检测机制

`RedisKeyConflictChecker`（位于 `lin-common-redis`）利用 Spring 的 `List<X>` 自动收集特性实现零耦合检测：

```java
@Component
public class RedisKeyConflictChecker {

    @Autowired(required = false)
    private List<RedisKeyPrefixProvider> providers;  // Spring 自动收集所有实现

    @EventListener(ContextRefreshedEvent.class)
    public void check() {
        Set<String> seen = new HashSet<>();
        for (RedisKeyPrefixProvider p : providers) {
            if (!seen.add(p.getPrefix())) {
                log.error("【Redis Key 前缀冲突】前缀 '{}' 被多个模块同时使用", p.getPrefix());
            }
        }
    }
}
```

**关键点——零耦合的实现原理**：

Spring 的 `@Autowired List<X>` 不是 Java 语言特性，而是 Spring DI 容器的扩展行为：它会自动扫描容器中所有类型为 `X` 的 Bean，全部注入到 List 中。冲突检测器不需要知道有哪些模块、它们叫什么、在哪个包里——Spring 替它完成了收集。

```
lin-common-core  ← RedisKeyPrefixProvider (纯接口，零 Redis 依赖)
    ↑                    ↑
    │                    │
lin-common-redis    lin-common-ratelimiter
(RedisKeys)         (RateLimiterRedisKeys)
    │                    │
    └── RedisKeyConflictChecker ─┘
       ↑ 通过 @Autowired List<T> 自动发现所有实现
       ↑ 不 import 任何具体模块类
```

### 5.4 启动时输出示例

**正常情况**（无冲突）：
```
[INFO] 检测到 2 个 Redis Key 前缀提供者，开始冲突检测
[INFO]   ✓ 前缀 'cache' → com.lin.redis.config.RedisKeys
[INFO]   ✓ 前缀 'rate_limit' → com.lin.ratelimiter.config.RateLimiterRedisKeys
[INFO] ✓ Redis Key 前缀冲突检测通过，共 2 个模块
```

**冲突情况**（两个模块用了相同前缀）：
```
[ERROR] 【Redis Key 前缀冲突】前缀 'cache' 被以下多个模块同时使用:
        [RedisKeys, BizRedisKeys]。
        请修改其中一个模块的 PREFIX 常量，避免运行时 Key 覆盖。
[ERROR] ⚠ Redis Key 前缀冲突检测到问题，请尽快修复
```

> 检测不阻塞启动——冲突会导致运行时 Key 覆盖，但不应该因为配置问题阻止应用起不来。

### 5.5 新模块接入步骤

假设要新增一个消息队列模块 `lin-common-queue`，只需三步：

1. **创建 Key 管理类**，选一个不重复的前缀：
```java
@Component
public class QueueRedisKeys implements RedisKeyPrefixProvider {
    public static final String PREFIX = "queue";
    public static final String DELAY_QUEUE = PREFIX + ":delay:";
    public static final String NORMAL_QUEUE = PREFIX + ":normal:";

    @Override
    public String getPrefix() { return PREFIX; }
}
```

2. **代码中统一引用常量**，而非硬编码字符串：
```java
// 之前：redisUtils.setCacheList("queue:delay:order", list);
// 之后：
redisUtils.setCacheList(QueueRedisKeys.DELAY_QUEUE + taskId, list);
```

3. **重启验证**——启动日志中自动出现冲突检测结果，确认前缀无重复即完成。

### 5.6 最终 Key 结构

经过 `KeyPrefixHandler`（全局前缀）和各模块前缀组合后，Redis 中实际存储的 Key 为三层结构：

```
<全局前缀>:<模块前缀>:<业务标识>:<动态参数>
   lin    : rate_limit : /api/user : 192.168.1.1:user001
   lin    :   cache    :  object   :    user:1001
   lin    :   queue    :  delay    :    order:20260428001
```

三层各自独立，全局前缀由运维配置控制（同 Redis 实例多项目隔离）、模块前缀由 `RedisKeyConflictChecker` 自动检测、业务标识由各模块内部常量管理。

## 6. 与限流模块的协作

`lin-common-ratelimiter` 通过 `optional` 方式依赖本模块：

```
lin-common-ratelimiter ──(optional)──> lin-common-redis ──> redisson ──> Redis
```

- 当项目同时引入两个模块时，`RateLimiterConfig` 检测到 `RedisUtils` 类存在，自动激活限流切面。
- 当只引入 `lin-common-ratelimiter` 而不引入 `lin-common-redis` 时，限流模块不会激活，不影响项目启动。
- 这种设计保证了双方可以独立演进，也可以方便地替换底层实现。

## 7. 优势总结

- **序列化一致性**：存入 Redis 的数据与接口返回的 JSON 格式一致，避免日期格式、大数字精度等差异。
- **全局 Key 前缀**：避免多模块 Key 冲突，支持同 Redis 实例多项目共享。
- **跨模块 Key 冲突自动检测**：通过 `RedisKeyPrefixProvider` + `RedisKeyConflictChecker` 在启动时自动校验，零耦合、零配置。
- **Key 可追溯**：每个 Key 的模块来源一目了然（`rate_limit:` / `cache:` / `queue:` 等），排查问题时不需全局搜索。
- **开箱即用**：引入依赖、配置连接即可使用 `RedisUtils`，无需手动创建 Client。
- **可剥离设计**：限流模块通过 optional 依赖实现松耦合，需要时激活，不需要时零成本移除。
