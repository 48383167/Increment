# 全局参数校验规范 (Validation)

**版本**: 2026-04-27
**涉及模块**: `lin-main`

## 1. 为什么需要框架级参数校验？

在传统开发中，如果前端传递了 10 个参数，后端通常要在 Controller 开头写大量的 `if-else` 来判断参数是否为空、格式是否正确：
```java
if (request.getUsername() == null || request.getUsername().isEmpty()) {
    return Result.error("用户名不能为空");
}
if (request.getAge() == null || request.getAge() < 0) {
    return Result.error("年龄不合法");
}
// ... 剩下的长篇大论
```
这种代码极具破坏性，它让 Controller 变得极其臃肿，难以阅读和维护。

## 2. 结构构造

我们通过整合 `spring-boot-starter-validation` (基于 Hibernate Validator) 实现了声明式的参数校验。主要体现在当前的 DTO 层和 Controller 层的配合。

### 2.1 声明式约束 (DTO层)
在接收请求参数的 DTO 类上（如本模块中的 `TestRequestDTO`），通过添加注解定义规则和提示语：
```java
public class TestRequestDTO {
    @NotBlank(message = "用户名不能为空")
    private String username;

    @NotNull(message = "年龄不能为空")
    private Integer age;
}
```

### 2.2 触发拦截 (Controller层)
在 Controller 接收参数时，加上 `@Validated` 注解即可激活校验：
```java
public Result<TestRequestDTO> validate(@Validated @RequestBody TestRequestDTO requestDTO) { ... }
```

### 2.3 异常转译 (Handler层)
校验失败时，框架会抛出 `MethodArgumentNotValidException` 或 `BindException`。我们在 `lin-core` 模块的 `GlobalExceptionHandler` 中专门对这两类异常进行了捕获。
提取出所有失败字段的 `message`，并用逗号拼接，最终包装成 `Result.error()` 返回。

## 3. 作用与优势

- **告别 IF-ELSE**：彻底将参数校验逻辑从 Controller 业务代码中剥离，Controller 回归原本“转发请求”的纯粹角色。
- **防君子也防小人**：即便前端做了表单验证，恶意用户依然可以使用 Postman 绕过前端发送非法数据。后端的全局参数校验能作为最后一道防线拦截非法数据，避免脏数据落库。
- **所见即所得**：校验规则与字段绑定在一起（DTO 中），其他开发者只需看一眼对象模型，就能清楚知道所有字段的约束条件。
